# BB V.G. — политика стабильных изменений production

Актуально на 25 июля 2026 года. Этот документ вводит обязательный порядок работы после повторяющихся инцидентов, когда локальное исправление кнопок, поиска, уведомлений или автоучастия нарушало соседний контур.

## 1. Цель

Главная цель любого изменения — сохранить весь пользовательский путь, а не только исправить один воспроизведённый симптом.

Рабочая версия считается стабильной только когда одновременно подтверждены:

- команды и кнопки Control Center;
- обнаружение Telegram-публикаций;
- классификация и сохранение колеса;
- доставка единственного разрешённого уведомления;
- отсутствие первичных уведомлений для реферального события и один итог только
  при подтверждённом участии хотя бы одного аккаунта владельца;
- независимое автоучастие всех настроенных аккаунтов;
- корректный итог и обновление исходной кнопки;
- сохранность состояния после параллельных workflow и перезапуска;
- свежие heartbeat Monitor и Control Center.

## 2. Замороженная поверхность legacy-композиции

Текущие runtime-подмены в `bbvg_monitor_main.py` и `notification_button_recovery.py` являются техническим долгом, а не рекомендуемым способом расширения.

**Новые runtime-подмены запрещены.** Нельзя добавлять:

- новое присваивание вида `module.function = wrapper`;
- новый `install()`, который повторно оборачивает уже установленную функцию;
- временную замену глобальной функции другого модуля без гарантированного восстановления;
- альтернативный Telegram consumer, параллельный runtime или второй путь отправки одного результата;
- локальную проверку, которая меняет пользовательский порядок ради одного частного инцидента.

Текущая поверхность зафиксирована в `tests/test_production_stability_guardrails.py`. Её расширение должно считаться ошибкой CI.

Исключение допустимо только как часть атомарного переноса, когда в том же PR:

1. определён один предметный владелец поведения;
2. поведение перенесено к владельцу;
3. прежняя обёртка или прежний путь удалены;
4. добавлены отрицательные тесты против возврата старого пути;
5. общее число runtime-подмен не увеличилось.

## 3. Обязательная матрица проверки

### Кнопки и callback

- главное меню открывается;
- «Назад» возвращает на правильный экран;
- «Активные колёса» открывается из карточки и итогового сообщения;
- `bb:p:<token>` относится только к одному событию;
- потерянный `button_contexts` восстанавливается только по однозначному активному событию;
- callback не превышает лимит Telegram и сохраняется после перезапуска.

### Поиск и классификация

- новый пост из основного источника обнаруживается;
- ссылка из текста и Telegram-кнопки извлекается;
- одно событие из нескольких источников создаёт одну пользовательскую карточку;
- новое поколение той же ссылки не подавляется старым состоянием;
- `active`, `not_started`, future availability и `inactive` не смешиваются;
- временный сетевой сбой не превращается в окончательное отсутствие события.

### Уведомления и дедупликация

- обычное нереферальное колесо отправляется ровно один раз;
- реферальное колесо остаётся во внутреннем состоянии и участвует в автоучастии;
  первичная Telegram/VK-карточка подавляется, а единый Telegram-итог разрешён
  только после подтверждённого участия хотя бы одного аккаунта владельца;
- `sent=0` без подтверждённого intentional suppression не записывается как успешная доставка;
- restart/recovery не создают вторую карточку;
- итог автоучастия отправляет только Control Center.

### Автоучастие

- основная event-попытка запускается после публикации актуального `state.json`;
- основной и второй аккаунт Вячеслава независимы;
- `xFLARXx` не подменяет результат аккаунтов владельца;
- ошибка одного аккаунта не пропускает остальные шаги и source recovery;
- Playwright нажимает только точную кнопку участия;
- технические `timeout`, `browser_error` и `unconfirmed` остаются повторяемыми, а не пользовательским отказом;
- подтверждённый success имеет приоритет над ранее сохранённой ошибкой.

### Синхронизация состояния

- Monitor, Control Center и auto-participation workflow объединяют состояние, а не перезаписывают чужой более новый snapshot;
- event identity включает `wheel_key + action_id + server_start_at`;
- runtime JSON не используется как место для архитектурных настроек;
- heartbeat/checkpoint-файлы не блокируют публикацию `state.json`;
- encrypted state и callback-схема сохраняют обратную совместимость.

### Живой production

- PR CI проходит на точном head SHA;
- Control Center валидируется и запускается на одном exact release SHA;
- после deploy подтверждены свежие heartbeat обоих процессов;
- Monitor показывает прогресс по всему текущему inventory;
- Control Center фактически выполняет единственный `getUpdates`;
- отсутствие heartbeat, остановка поиска или ошибка callback считаются неуспешным релизом.

## 4. Порядок изменения

1. Создать неизменяемую backup-ветку от текущего production-состояния.
2. Работать только в отдельной ветке и PR.
3. Зафиксировать воспроизведение проблемы тестом до изменения поведения.
4. Определить фактического владельца функции, callback и state-полей.
5. Изменить минимальное число предметных владельцев без нового слоя поверх старого.
6. Запустить архитектурный guard, targeted tests, полный `pytest`, production acceptance, preflight и security audit.
7. Не менять `control_center_release.txt` в функциональном PR.
8. После merge создать отдельный release commit только на проверенный exact SHA.
9. Проверить живые heartbeat и критический пользовательский путь.
10. Только после подтверждения production создать новый стабильный backup.

## 5. Автоматический откат

Автоматический откат должен выполняться к последнему подтверждённому production SHA, если после релиза подтверждено хотя бы одно из условий:

- Control Center не принимает команды;
- Monitor не завершает итерации или не проверяет inventory;
- критический callback не работает;
- новое обычное колесо не попадает в состояние;
- обычная первичная карточка не доставляется;
- автоучастие не запускает обязательные независимые этапы;
- runtime-state повреждён или потерял обязательный раздел.

Откат не должен возвращать пользовательский state к старой копии без отдельной миграции. Код и release marker откатываются отдельно от актуальных runtime-данных.

## 6. Приоритет дальнейшего упрощения

Рефакторинг выполняется небольшими атомарными этапами:

1. Control Center: один владелец callback и построения кнопок.
2. Monitor: один владелец классификации и lifecycle события.
3. Уведомления: один владелец delivery identity и suppression.
4. Автоучастие: единая модель результата аккаунта без подмен функций.
5. Recovery и state merge: один явный протокол объединения.

Нельзя переходить к следующему этапу, пока предыдущий не прошёл всю матрицу и не подтверждён в живом production.


## Telegram: обязательная проверка запуска и данных

- Команда `/start` обязана либо открыть меню, либо отправить понятное сообщение о временной недоступности; молчаливое исключение запрещено.
- Ошибка чтения `state.json`, `source_stats.json`, `source_health.json` или `public_sources.txt` не считается пустым состоянием.
- При временной ошибке сохраняется последний подтверждённый snapshot; если его ещё нет, запуск явно сообщает о недоступности данных.
- Каждый кандидат Control Center до выпуска выполняет `scripts/telegram_start_state_smoke.py`.


## Устранение периодического цикла ложных сбоев

- Heartbeat-коммиты и runtime JSON не являются deployment-событиями и не запускают полную диагностику.
- Полная health-проверка выполняется по независимому расписанию; пяти минутный watchdog только восстанавливает действительно зависший процесс и не отправляет пользовательские диагнозы.
- Долгоживущий Control Center продлевает собственную смену; параллельный ежечасный полный запуск запрещён.
- Сетевые, heartbeat- и runtime-инциденты открываются только после повторного подтверждения.
- Сообщение «работа восстановлена» отправляется только после устойчивого здорового состояния, а не после одного удачного запроса.
- Ошибка чтения GitHub не может заменить последний подтверждённый Telegram snapshot нулевыми данными.
